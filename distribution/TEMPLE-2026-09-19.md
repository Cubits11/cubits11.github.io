# Temple outreach — what the repositories actually support

Prepared 2026-09-19. Nothing here has been sent. This document narrows a
twenty-five-person outreach plan to one prepared issue, one collaboration
proposal, and one request that would clear the oldest actionable blocker in
the programme. It records why the other twenty-two are not issues.

## The question I asked of each candidate

Every technical interaction this programme has spent — four of twelve, in
`distribution/outcomes.yaml` — rests on one precondition: **the target's own
public artifact contains per-item outcomes for two or more systems scored on a
shared item pool.** IBM keeps `result_<model>_<data>.pickle`; GuardBench
writes `results/<dataset>/<model>.json` keyed by item id; BELLS released 170
rows with five supervisor columns. That precondition is what makes the ask
answerable without a meeting, and it is why the ask is always the same: you
hold the joint outcome, publish it or compute it.

So the question is not "is this person interesting." It is: **does a public
repository exist where two or more systems were scored on one shared pool, and
the per-item outcomes are not released?** Interest without that artifact makes
an email, not an issue.

## Per-researcher: what work is actually available

### Eduard Dragut — the one empirical ask, and one real research question

**The ask** is prepared in
`distribution/issues/2026-09-19-scier-joint-predictions.md`. SciER releases
4,243 entity mentions across two test splits at commit `db347813` and reports
PURE, PL-Marker and HGERE on them. It releases no predictions, so the count of
mentions all three missed is bounded and not determined.
`scripts/reanalyze_scier_testset.py` establishes the denominator and states the
integer it cannot compute.

**Why it is worth a budget slot beyond the integer itself.** The census
currently surveys guardrail benchmarks. Every row is a safety artifact, so a
sceptic can read the missing-column result as a fact about one community's
reporting habits. SciER is scientific information extraction with no safety
stake and no adversary, and the joint outcome is withheld there too. One
confirmed instance outside the safety domain distinguishes "safety benchmarks
under-report" from "multi-system evaluation under-reports," and the second is
the stronger and more defensible claim. **I have not shown this. One repository
is an instance, not a survey**, and a single reply would license only the
observation, not the generalisation.

**The deeper collaboration — `DynClean`.** Distantly supervised NER derives
labels by aggregating several noisy labelling sources. That is the same formal
object this repository studies: several imperfect detectors over one item pool,
and a joint behaviour that is not a function of the marginals. Denoising
methods in that literature routinely assume conditional independence between
sources given the true label — the identical assumption this programme's E3
line exists to test. A shared question stated precisely: **when does
source-marginal accuracy determine aggregate accuracy, and what is the
identified set when it does not?** That is a joint paper, not an issue, and it
is the strongest intellectual fit among all twenty-five candidates.

### Anduo Wang — the deepest methodological fit, and it is not an issue

`python3 scripts/direction.py` prints the admissibility plane with four absent
conjuncts: U, Q, V, T. The binding one is **E — "the runner actually consumes
that specification" — which reads `partial`.** `CLAUDE.md` states the limit
exactly: `research/contracts/validate_contract.py` "checks structure, threshold
direction, planned pool identities and planned marginal preservation. Passing
establishes internal consistency, **not runtime conformance**."

That gap — a specification declares X, and nothing proves the execution did X —
is refinement checking. It is the problem Declarative Network Verification
addresses for routing protocols: logic-based axioms capture semantics, and a
proof establishes that an implementation satisfies a property. The `wadaries`
account carries a Z3 fork and `ravel`.

**The concrete proposal:** express `contract.json` as a logical specification
and discharge runtime conformance as a proof obligation over an execution
trace, instead of as a structural check in Python. If that reduction works, E
moves from `partial` to `enforced`, and the ontology sentence this programme
opens with — "a passing execution must demonstrate that the computation
observed was the computation declared" — acquires a mechanism rather than a
restatement.

**Non-claims.** I have not shown the reduction is sound, tractable, or worth
the proof burden on experiments this small. The programme's `BUDGET` rule
already holds infrastructure at 2 against work at 4, and this is
infrastructure. It is a conversation to have, explicitly, as infrastructure —
not a step to take because the fit is elegant.

**Correction to the 2026-09-19 report:** the proposed connection to
"challenging Ghost-Ark's authorization and evidence boundaries" is not
supportable from here. `ghost-ark` is read-only from this repository per
`CLAUDE.md`, and `GA-001`'s support URL is not reachable from this host. The
conformance framing above is anchored in this repository's own declared gap
and needs nothing from `ghost-ark`.

## The budget arithmetic

`distribution/outcomes.yaml` sets a stop rule: **at 12 technical interactions
with 0 qualified outcomes, stop replying** and move to upstream contributions
and direct author outreach. Four are spent. All four are still open with zero
comments. The observed rate is 0 for 4.

Three consequences follow, and they are the reason this plan is one issue
rather than five.

**1. Issues consume the budget; emails do not.** Every entry in
`technical_interaction_log` is an issue on someone else's tracker, and
`scripts/outcomes.py` requires each entry's `url` to begin with `http://` or
`https://`. An email has no URL and cannot be recorded there under the current
schema. So email outreach to Temple does not spend the budget, and each
GitHub issue spends one of eight. This is read off the validator, not decided
here; if the owner wants emails counted, the schema needs a field, and that is
a decision to make deliberately.

**2. Spending eight slots on Temple would confound the stop rule's own
result.** `distribution/QUEUE.md` row 9 requires "a supported diagnosis, with
exactly one changed variable when the rule fires." The four spent interactions
went to benchmark maintainers who hold per-item outcomes. Academics who hold no
such artifact are a different audience *and* a different ask. Fire the rule on
a mixture of both and the resulting statement — "the absence of qualified
outcomes after real technical engagement is itself a result about the
audience" — is not supported, because two variables moved. The SciER ask is the
same kind as the four already spent, which is precisely why it is the one that
may be sent.

**3. The programme's binding constraint is not contacts.** It is fourteen open
blockers, oldest seventeen days, none clearable by writing. Twenty-five new
contacts do not clear one. Five cold viewers clear the one that gates
distribution entirely.

## A defect found while running the repository's own gate

`python3 scripts/verification_manifest.py` exits 1 on a clean tree at `f2249c1`,
before any change in this session: eleven claim support URLs return
`HTTP Error 403`. Every one is an out-of-scope repository, and
`Cubits11/cubits11.github.io` is the only GitHub repository that returns 200
from this host. The 403 is this session's egress proxy, not a broken binding.

The relevant code is `transport_failure()` in `scripts/verify_claims.py`, which
deliberately excludes `HTTPError` from transport failures because "the server
did answer — a 404 or 410 on a bound support URL is a real finding about the
binding." That reasoning holds for 404 and 410. It does not hold for 403, which
is the canonical status for *an intermediary refused you*, and which here is
returned by a proxy that never contacted the origin. `CLAUDE.md` states the
governing doctrine: a check that could not be evaluated "is not a pass," a gate
"must not proceed on an unknown," and the result may not be recorded "as a
refutation." Under that doctrine a proxy 403 belongs in exit 2, not in the
failure count.

**I have not changed it.** `scripts/verify_claims.py` is pinned by `sha256` in
`claims.yaml` with a `local_content_change` trigger, so editing it fails the
registry until the claim is re-pinned and `last_reviewed` bumped. Folding a
verifier change into an outreach commit is exactly the silent scope change this
repository is built to prevent. It is recorded here as an owner decision.
